Telegram

AICR 支持 telegram_bot，每次发布一条聚合报告，通过 HTTP 接收 help、chat-id、review、status 四种命令。 命令必须为单行。/aicr@TestBot 后或消息末尾含换行时，命令会被拒绝且不产生回复。 按钮和自然语言请求未纳入此实现。

创建和安装

Section titled “创建和安装”

打开 @BotFather，发送 /newbot，按提示设置显示名和唯一 username。 把 Bot API token 通过部署环境注入 AICR_TELEGRAM_TOKEN，不要贴入浏览器地址栏、截图或聊天。 创建流程见 Telegram 官方教程。

id 填入 im.connections.bot.bot_id，username 用于 /aicr@你的机器人用户名。 它们都不是群 ID；命令授权的 actor 则是人的数字 ID，不是人的 username。 依据：getMe。

获取群 ID

Section titled “获取群 ID”

私聊由用户先启动 Bot；群聊先添加 Bot 并允许发送消息，普通群不需要管理员权限。 保持 privacy mode，群中使用 /aicr@BotUsername 定向命令。 先通过已有且授权的 Bot 管理流程取得数字 chat ID，以及精确用户授权需要的 actor ID，再启用 binding。

显示名和私有邀请链接不能传给 getChat 反查群 ID。公开 @username 也可能指向广播频道，须核对返回类型。 设置 webhook 前，可在群内发送定向命令，从 getUpdates 的 message.chat.id 取得群 ID；不要输出 token 或其他聊天内容。 polling 和 webhook 不能同时使用。未知用户不能通过 chat-id 自行加入精确用户白名单。

若定向命令仍没有更新且无法复制群内消息链接，可在设置 webhook 前临时使用 getUpdates 的 allowed_updates: ["message", "my_chat_member"]，从机器人的成员变更事件取得群 ID。 请群管理员从 getMe 确认的机器人页面重新加入目标群；只读取该 Bot 与目标群的事件，核对 my_chat_member.chat.id。 随后调用 getChat 核对群类型，并用 getChatMember 查询机器人自身的成员状态和发言权限。 不要改用广播频道、猜测 ID 或为排障关闭 privacy mode。生产 webhook 注册仍使用 ["message"]，不删除待投递更新。 依据：getUpdates、Update、getChatMember。

ID 使用带引号的十进制字符串，取值范围为 -9007199254740991 至 9007199254740991；Bot 和用户 ID 为正数，群 ID 可以为负数。仅支持已建立的 private/group/supergroup； forum/topic、channel、business、匿名 sender_chat、Bot 自己发送及编辑更新不触发审查。 依据：Bot API、privacy mode。

发送报告

Section titled “发送报告”

从 example/telegram-bot.yaml 开始， 替换所有合成 ID 并设置 token 环境变量。output 引用 im.connections.bot 和准确目的地， ws.outputs.summary: [report] 选择报告渠道。实际审查前合并已有 VCS/LLM 配置。 file-only 可以发送报告；干净结果默认使用 publish_if_summary，覆盖方式见输出策略。

模板仍按 named、workspace、内置的正常优先级选择。总预算为 3900 个 UTF-16 单位， 包含截断提示及可用的安全报告链接。Telegram 使用显式 UTF-16 entities，不开启 parse_mode。

同次审查还通过 issue 渠道发布完整报告时，AICR 先发送 issue，再使用其已确认链接发送简要通知：标题、问题数、严重级别/分类/位置和详情链接，并保留作者提醒。分析、建议和代码留在 issue。没有可用的已确认链接（包括 issue 写入失败）时，渠道仍发送完整报告。此行为不依赖渠道配置顺序，也不需要新增渠道选项。

报告按 Review target、Summary、Problems 分节，标题和严重级别使用加粗实体，问题标题保持单行。 代码使用独立的 code/pre 实体，围栏语言提示写入 pre 的 language，不作为正文显示。 含行内代码的加粗标签会分段，避免样式与代码实体重叠。 CRLF 与正文多余空行会归一化；内部审查标记不显示，代码示例内容保留。 实体及嵌套规则见 Telegram 格式说明。

验证流程

Section titled “验证流程”
  1. 在配置的用户和会话中执行 /aicr@TestBot help、/aicr@TestBot chat-id。
  2. 用合成仓库中的真实固定提交执行 /aicr@TestBot review demo 0123456789abcdef0123456789abcdef01234567。 Git revision 为 7–64 位十六进制，配置的 P4/SVN 使用固定正整数。
  3. 保存 request ID，执行 /aicr@TestBot status <request-id>。
  4. 核对完整报告只发到配置的输出目的地；来源会话只收 ID、状态和查询说明。 status 保持同 actor、连接、会话和当前允许的仓库。

ACK 只代表接收，不代表完成分析。后台 readiness 核对平台身份及已配置目的地元数据，缓存 300 秒； 不可用时拒绝接收。本地接收预算为一秒，callback 不等待 VCS、模型、readiness 网络请求或消息发送。 后台在过期前刷新；刷新期间保留原有效期限，成功才续期，失败立即停用目的地。验证命令回复时须跨越缓存刷新周期。

运维与排障

Section titled “运维与排障”

401 时核对 X-Telegram-Bot-Api-Secret-Token 与配置的 webhook secret。群命令必须指向 getMe 返回的 username，不能用显示名。blocked/403 需要用户或群调整；群迁移不会自动改变配置 chat ID。429 的 parameters.retry_after 单位是秒。注册超时后先查 getWebhookInfo，再决定是否执行新的 apply。

出站超时时，从运行中的 Node 容器核验平台 API 访问。若部署使用代理，按 运行时 HTTP 代理配置核验；宿主请求成功不能代替 readiness。

每次新的 VCS、分析和远端发布前复查当前权限，执行内容继续使用接收时的 snapshot。 停用 binding、connection 或 callback 可停止新的授权工作。通过正常配置发布流程轮换秘密，保持平台身份稳定。 改变 app/guild/Bot 身份后，旧通知不会转发给同名新连接。

完整且目的地匹配的回执才是 delivered；明确失败是 rejected。 进入 POST 后，仅明确的 429 允许到期重试回复。丢失响应、服务端失败和过期 sending lease 保留为 unknown，不会自动重发。 先查远端消息与 journal/outbox，再决定是否创建新请求。

进入 POST 前的本地配置、凭据或存储异常按持久 due time 退避。这些安全重试与明确限流重试共用最多五次的预算，耗尽时为 failed。可能已经发送或回执落库失败时保留 sending 围栏，租约到期后为 unknown。日志只保留固定错误码，不记录上游原始错误。

回滚前停用 ingress 并排空 worker，再更换程序或恢复兼容备份。迁移 013 新增版本化 reply payload 列； 不要删除请求、journal/outbox 来清除 unknown。注销平台资源前核对当前归属，只处理本部署拥有的资源。

仓库测试使用 HTTP 替身和真实本地存储；真实平台需单独凭据并独立验收。 本地通过不代表客户端呈现或公网回调已验证。

Section titled “提醒审查作者”

在输出渠道将审查身份映射到人的数字 Telegram user ID；不能填 username、Bot ID 或 chat ID：

Telegram Bot API 没有完整成员目录接口；使用显式映射或下方文件目录。授予管理员权限也不能列出所有成员。AICR 追加 tg://user?id=… 的 text_link 实体，offset/length 使用 UTF-16 单位；实际提及仍受 Telegram 的群成员、此前联系和隐私条件约束。依据：格式与 ID 提及。
