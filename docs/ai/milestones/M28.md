## 渠道终态判定矩阵

- 问题在 publishSummary 阶段缓冲/收集：`raw.collected === true` 或 `buffered` → `pending`（未发送）。
- HTTP 4xx（除 408）→ `failed`；无响应、408、5xx、部分发送 → `unknown`。
- update_existing 的 PR review、指纹 reconcile 的 problem issue 可降低重复；
  其余渠道（gitlab_mr_review、gitea/github_issue、IM bot、always_new）的 `unknown`
  自动恢复可能重复多条消息，尤其是部分报告和内部 HTTP 重试。人工核查依据为批次 `publications` 回执。

## 未提交代码复审修复

回归测试先复现了 9 项失败，再修复以下边界：

- 复合 publisher 原先调用完所有渠道才保存回执，且执行器直到发布结束才报告租约丢失。
  现在每次调用前检查租约、返回后立即保存回执；持久化错误通过取消信号穿过编排层的
  dispatch 错误捕获，停止后续远端调用。
- 原先单次成功会覆盖同渠道的先前失败，多摘要也会提前确认渠道。现在失败在本次执行内
  保留，最后一条摘要完成前保持未确认；缓冲摘要不算已送达，空的成功 reconcile 可确认。
  `attempts` 按触及渠道的执行器尝试计数，连续相同失败也会递增。
- Redis Lua/cjson 会把嵌套空数组改成对象。检查点改为不透明 JSON 字符串，三后端共享
  合同测试验证保存、租约回收后的嵌套数组/对象完整性；读取仍兼容旧对象形式。
- 载荷、回执或最终记账超限时清除旧的部分状态，避免恢复时信任过期回执；损坏的载荷
  或回执拒绝执行。原模型、token、费用、请求/重试/兜底次数随分析结果保存；全部渠道已经
  确认时恢复仍记作 published，不误记 skipped。
- 配置片段发现先识别已知根键，不再把 YAML 解析失败或混入未知根键当作非配置跳过。
  管理 API 测试还验证只暴露回执，不返回分析载荷。

定向证据见 `build/logs/plan-review-red.log`、`plan-review-focused.log` 与
`plan-review-stores.log`。最终门禁使用仓库基线顺序，日志前缀
`build/logs/plan-review-final-`；本地真实服务由隔离 Redis/PostgreSQL 实例提供。
运行时审查 prompt 无需改动：修复的是宿主发布与持久化边界，模型输出工具合同保持不变。
