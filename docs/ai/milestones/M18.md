# M18:配置来源合并、路由图与发布服务(P3)

## 状态

实现与验收记录(2026-09-12)。稳定合同见 `../architecture.md` §3.15,设计与
阶段定义见 `docs/superpowers/specs|plans/2026-09-11-workspace-config-*`。
运行时 generation 固定(P4)、管理员 API(P5)与管理表单(P6)仍是
`Plan.md` 待办;运行时消费的配置来源仍是 YAML 文件。

## 目标

Workspace 动态配置路线图的 P3 阶段:raw file + DB + defaults 合并、
changeset 原子变更、v2 路由执行图与旧路由兼容、prepare → CAS →
audit/snapshot → install 发布事务、revision restore、无副作用 preview
与 readiness 诊断。另含同轮 P2 组件审查驱动的并发加固。

## 已交付

- **来源合并**(`packages/core/src/config-source.ts`):原文解析(位置
  sourceMap/大小上限/`__proto__` 拒绝)→ legacy 转换 → 文件/DB 合并 →
  单次 schema 解析(defaults 只应用一次)。文件显式配置优先并锁定
  (实体锁 + 全局叶字段锁);同名 DB 记录被遮蔽但保持可见/可导出/可
  删除;显式空数组/false/0 与缺省区分;每字段 provenance 可查询。
- **Changeset**(`applyConfigChangeset`):`create/update/delete/rename/
  set-enabled` 操作六类实体集合(providers/model_groups/triggers/
  channels/workspaces/routes),`set/unset` 操作全局叶路径;`file_owned`
  拒绝文件拥有项;capability 校验随记录写入;routes 集合要求
  formatVersion 2。
- **执行图**(`config-compiler.ts`):v2 `routing.rules`(显式 priority、
  AND 条件 + OR 列表元素、空数组关闭输出、缺省继承)与旧
  `outputs.routes` 兼容图(数组顺序、空数组回退、`*_pr_review` 首
  channel 回退)统一为同一 resolve 入口。同 trigger 双代控制
  `routing_conflict`;优先级同分且 workspace/analysis/outputs 经
  stableSerialize 比较冲突即 `ambiguous_route`;一个事件至多一条规则,
  无隐式 fan-out。分析参数全局 → defaults → 实例 → 路由规则四层合并,
  数组整体替换。发布校验拒绝未知 workspace/model group/channel/
  trigger 引用,并拦下 PR inline channel 绑定非 PR 目标(R07)。
- **发布服务**(`config-publish.ts`):prepare 纯函数(不评审/不建
  webhook/不调模型/不拉镜像);`commitChangeset` CAS 为线性化点;
  snapshot 写入或本机 install 失败返回 `committed_activating`,不谎报
  rollback;`getConfigOperation` 按 operationId 回答响应丢失;audit
  diff 只含实体名与全局路径(S06)。`prepareConfigRestore` 以当前文件
  锁/capability/secret 约束重新校验历史文档,发布为更高 revision,
  永不 downgrade head(C12/S07)。
- **Preview 与 readiness**(`config-preview.ts`):changeset 预览零写库
  (测试断言 head/revisions/audit 读后皆空);路由预览复用准入同一
  resolve 函数(R13 不漂移),输出规则命中、workspace 绑定、完整最终
  目录(不只模板片段)、模型组与输出 channel;`diagnoseConfigReadiness`
  报告 disabled/store_unavailable/empty/file_config_mismatch/
  snapshot_missing/ready 六态。
- **v2 effective schema**(`config.ts`):`parseEffectiveConfig(input,
  formatVersion)` 区分文件 v1(拒绝 `routing`)与合并后 v2 文档;
  `routingRuleSchema` 严格限制 analysis 可继承子集(model_chain/
  triage_model_chain/agent/sandbox/review/compression),不接受 provider
  凭据或 VCS 连接。错误码新增 `routing_invalid`/`routing_conflict`
  (config-format.ts 合同词汇表 pin 测试同步登记)。
- **P2 并发加固**(同轮 reviewer 深审后修复):
  - `stats.pg.ts`:project upsert 改 `INSERT ... ON CONFLICT DO NOTHING`
    - 重 SELECT;run 记账整体包进 drizzle 事务,23505 容忍收窄到
    `review_runs_pkey`,消除新项目身份竞态下的静默丢账;rollup 改
    upsert 支撑同事务并发。
  - PG/SQLite `deleteSnapshot` 改单条条件删除(`WHERE pinned=0 AND
    ref_count=0`),消除 GC 与迟到 pin 的 TOCTOU(§7.2 已签收任务
    找不到 snapshot 的不变量)。
  - PG/SQLite `writeSnapshot` 并发幂等(ON CONFLICT/INSERT OR IGNORE
    - 重读校验 content_hash),兑现同 id 同内容返回已存记录合同。
  - Redis `LUA_COMMIT` 在脚本内由 active 推导 revision 序号,不再信任
    调用方预读;PG config store 首启 CREATE SCHEMA + 迁移罩会话级
    advisory 锁(与业务库同模式)。
  - `migrate=verify` 服务端路径只读化:ledgerExists 探测缺失账本时按
    全 pending 计算,CREATE SCHEMA 仅 auto 模式;与 CLI 行为一致。
  - `config-store-factory` 接受 `postgres.url` 回退(url_env 优先),
    消除与 bootstrap 业务库的分裂;`storage.database` 连接串属既有
    部署合同,§8.4 env-only 边界针对新 config-source 实体。
  - bootstrap:过期 admin session 每 15 分钟有界 sweep(unref 计时器,
    close 即停);构建失败按已建资源逆序 close;deferral 在 PG 后端
    把 upsert 纳入串行队列(sqlite 保持同步可见)。

| 显式路由绕过准入，预览布局和有效值不准确 | 始终解析 workspace binding；空 v2 路由保持 v2，处理 catch-all 冲突；预览空库 baseRevision 为 null，读取有效实体与 provider fixture 字段；未知 op 拒绝，`config-preview.test.ts` / `config-review-regressions.test.ts` |
