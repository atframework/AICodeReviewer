# Managed Problem Issue Lifecycle

Read this when changing `gitea_problem_issue`, `github_problem_issue`, issue modes, scope fingerprints, resolved-action behavior, file-scope guards, or reconciliation tests.

## Managed problem issue lifecycle

- `gitea_problem_issue` and `github_problem_issue` support:
  - `consolidated` (default): one target-aware issue per scope. Push scopes use `headSha`, PR/MR scopes use the pull number (falling back to `headSha`), and other targets use the repository scope.
  - `per_commit`: one independent issue per commit. Never run cross-scope cleanup for this mode.
  - `per_problem`: one issue per problem fingerprint.
- Consolidated bodies carry commit, open-fingerprint, and per-problem fingerprint markers. Problem headings must parse both `file:line` and `file:start-end`; retained and resolved rendering must preserve `endLine` and enough of the original diagnostic for semantic verification.
- Same-scope updates verify commit order: same-commit replay cannot resolve problems, older/diverged commits are skipped, and compare failure updates without classification.
- Cross-scope reconciliation is consolidated-only and fail-safe:
  - require both stored/current commits and an explicitly successful ancestry comparison;
  - filter current findings to fingerprints owned by the old issue, including its open and resolved markers; return only currently reported resolved fingerprints to the active set, leaving other resolved history outside missing-finding verification;
  - treat reviewed-and-missing fingerprints as candidates, then require the injected `ProblemResolutionAnalyzer` to confirm them against current source; retain unreviewed, unconfirmed, legacy-no-diagnostic, and analysis-failure candidates, and skip rewriting if retained metadata is incomplete. A genuine empty review (including `lgtm`/`no_reviewable_code` skip-classified runs) instead offers every still-open stored fingerprint to the analyzer — the file-coverage pre-filter only applies when findings exist or no analyzer is configured;
  - preserve the old scope marker and historical summary;
  - apply `resolved_action` only when no open fingerprint remains.
- Empty reviews use the same per-fingerprint path. With a resolution analyzer, every still-open stored fingerprint becomes a verification candidate, not only fingerprints inside the current diff; without one, the file-coverage guard still retains uncovered fingerprints. Same-scope markerless bodies no longer use the legacy whole-issue close fallback because they lack a diagnostic the model can verify; different scopes never use that fallback.
- `reviewedFiles` flows from `ReviewSummaryPublishOptions` through bootstrap to the third `reconcileProblems` argument. Do not remove or bypass it.
- Reconciliation only runs for real review outcomes, never for failure notices: `ReviewSummaryPublishOptions.skipReconcile` makes the `github_problem_issue` / `gitea_problem_issue` bootstrap wrappers return `[]` without calling `reconcileProblems` (and without consuming the per-publisher `reconciled` flag). `publishTriggerErrorReport` sets it alongside `bypassNoProblemsPolicy` so a failed/timed-out analysis (empty problem list) cannot resolve or close managed issues. A normal genuine-empty review omits it so resolved findings still close.
- The no-problems policy gates visible summaries only, never lifecycle: the three problem-issue wrappers advertise `reconcilesManagedIssues: true`, so the composite publisher (`createCompositeOutputPublisher`) and the orchestrator still route genuine empty reviews (empty summary + `reviewedFiles`) to them even when every channel suppresses zero-problem output. `resolved_action: none` remains the lifecycle opt-out.
- Per-problem bodies embed `<!-- aicr:file=<path> -->` and may parse legacy `Location: path:line`. Missing file metadata with scoped review input must remain unresolved.
- Same-scope duplicate consolidated issues from prior races are resolved after the primary issue is updated.
- Production bootstrap injects one cached resolution analyzer per review and uses the model/client from the workspace-resolved `triage_model_chain` group (instance → defaults → llm → workspace main group); when no layer selects triage, reuse that workspace's code-analysis model/client. Initial and confirmation calls share the review's cumulative `runSpend` and `per_run_usd` checks without losing the selected triage route. Duplicate cleanup remains deterministic because it reconciles managed identity, not code resolution.
- The analyzer verifies the original failure mechanism, not mandatory adoption of every suggestion. Negative/missing verdicts receive one bounded confirmation pass; earlier explicit approvals survive its failure. Reject duplicate verdicts and evidence-free approvals, including a valid verdict duplicated by an entry with an invalid type or missing evidence in either order. A model reason saying a fix exists can conflict with its boolean, so prompt for evidence before the verdict and recheck negatives; never invert a boolean by matching prose. Inspect `problem resolution analysis completed` by run/commit/fingerprint to distinguish `source_unavailable`, `missing_or_invalid_decision`, `analysis_failed`, and `model_unresolved`. Tests: server `problem-resolution.test.ts` and `runtime-generation.test.ts`.
- Partial consolidated updates retain cumulative `aicr:resolved_problems` and bounded `aicr:problem-meta` records, render original diagnostic excerpts, and remove a resolved fingerprint when it is reported open again. Recurrence must trigger a body update even with zero newly resolved fingerprints: reading resolved markers only in the renderer, or retaining a resolved-count-only write guard, loses that transition. Final closure writes the completed body and state together. Bodies have a local 65,536 UTF-16-unit budget: omit resolved Base64 metadata first, then visible resolved details, while preserving open content and complete fingerprint markers. If required content still exceeds the budget, fail before create/update/close or lifecycle comments; never truncate markers or claim closure. Truncate visible diagnostics by grapheme. Exercise cumulative partial fixes and `mark_resolved` through actual provider payloads in `managed-issue-recurrence.test.ts`. Closed issues remain outside the open-issue reconciliation window. Unmarked legacy resolved lists cannot restore fingerprint history.
- On `mark_resolved` closure, include the Resolved prefix before selecting the
  body's metadata/detail degradation. An individually legal unprefixed body
  can exceed the budget after prefixing; reserve it in the final renderer rather
  than rejecting after degradation has finished. Test near-limit bodies and
  oversized historical bodies through all three providers in
  `managed-issue-recurrence.test.ts`.
- Titles stay output-owned and concise; `aicr.publish_summary.title` only affects the summary rendered in the body. When every surviving problem is retained from an unreviewed file, refresh the generated severity/count/location prefix but preserve the existing descriptive suffix instead of promoting retained placeholder prose into the issue title.
- Gitea applies `auto_tag` and `reviewed_tag` at issue creation through `body.labels`.
- Assignment: preserve event login → email mapping → linked commit author → retained pusher order. Blacklist/disabled assignment must stop API fallback; OWNERS remain independent. Gitea uses `/git/commits/{sha}`, GitHub `/commits/{sha}`; Gitea unlinked push authors send `username: ""`. Cache in-flight lookups and misses, and test actual URLs/payloads through bootstrap. Retry creation only for explicit 422 assignee validation, never generic 4xx or unknown POST outcomes. See [assignment rules and API sources](../../../../docs/output-channels.md#assignee-resolution), `managed-issue-assignment.test.ts`, `bootstrap.test.ts`, and `webhook-utils.test.ts`.
- GitLab (`gitlab_problem_issue`): same lifecycle model; project = numeric ID or URL-encoded path (`project_id` overrides the trigger/workspace repoRef), labels are comma-separated names (auto-created on issue create; severity labels still go through the labels API for colors), ancestry uses the `merge_base` endpoint, and `resolved_action: delete` uses `DELETE /projects/:id/issues/:iid`. Assignment resolves usernames to numeric IDs via `GET /api/v4/users?username=`; there is no commit→login lookup. Two silent-drop traps verified on CE 19.4: assignees must be project members, and CE ignores the plural `assignee_ids` field (multiple assignees are Premium) — always send a single assignee as `assignee_id`. A third race: `ProjectTeam#member?` reads the asynchronously populated `project_authorizations` table, so a member added seconds earlier may still be dropped — live fixtures poll `read_project` with an impersonation token before publishing. Live evidence: `gitlab-assignment-live.test.ts` and `gitlab-flow-live.test.ts` via `tests/services/with-gitlab.sh`.
