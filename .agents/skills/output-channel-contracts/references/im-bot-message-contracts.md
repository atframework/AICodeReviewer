# IM Bot Message Rules

Read this when changing Feishu, WeCom, DingTalk, Slack, or other IM bot rendering, markdown transformation, author mentions, or agent-output repair behavior.

## IM bot message rules

IM bot reports share the structure and content rules below; payload limits and formatting remain platform-specific.
Feishu/WeCom/DingTalk/Slack transformations live in `im-markdown.ts`; Discord/Telegram and social-message budgets live in `social-im-markdown.ts`.

- `publishAggregatedProblems` includes every problem's complete `message`, optional `suggestion` and code reference, subject only to the outgoing platform byte limit below. Preserve paragraph and code formatting.
- When the summary route also records the full report as a managed issue, Feishu dispatchers receive a `detailLink` and render the linked-issue card; the channel's `issue_link_card` (`brief` legacy count-only, `titles` default per-problem titles, `full` complete sections) selects the card content, and the trailing mention element is preserved in every mode. The zero-problem card stays headline + link.
- Issue channels run before linked IM notifications regardless of route order. Slack/Discord/Telegram reuse `buildImIssueLinkSections` with the default title list, preserving the issue link and resolved author mention through truncation. Without a confirmed issue URL they retain the full report. Recover links from confirmed journal responses (`html_url`/GitLab `web_url`); never synthesize issue URLs. Cover actual payloads and skipped-channel recovery in `social-im-issue-notifications.test.ts` and `bootstrap.test.ts`.
- IM reports stay sectioned as **Review target → Summary → Problems**; problem locations must come from structured `aicr.report_problem` data, not prose-only summaries.
- For Slack/Discord/Telegram, normalize CRLF and prose spacing through `normalizeSocialImMarkdown` while protecting fenced/inline code. Hide `aicr:` comments only at the IM presentation boundary, retaining Git bookkeeping. Verify shipped `.hbs` files as well as inline templates; problem labels must stay on one line. Slack fence language hints are not code content; Telegram uses `pre.language` and must not overlap bold with code/pre entities. Cover actual payloads in `social-im-publishing.test.ts` and formatter boundaries in `social-im.test.ts`.
- Use the shared code/link atoms in `markdown-code.ts` for conversion and truncation. Balanced URL parentheses and variable-length backtick delimiters stay indivisible; code spans/fences never become partial output. Accept HTTP URL schemes case-insensitively in both conversion and send validation, and compute Telegram entities from final UTF-16 text. Cover nested parentheses, multi-backtick truncation, uppercase schemes and Slack blockquotes in `social-im.test.ts`.
- Agent CLI free-form stdout is not a publishable final report; repair to structured JSON/XML tool calls before summary-channel dispatch.
- If the repair result is still prose but explicitly says there are no actionable problems or no reviewable code, normalize it to `aicr.skip` (`lgtm` / `no_reviewable_code`) instead of publishing the generic format-repair fallback to IM.
- Summary text that says issues were found is not a problem record. If `problemCount` is zero, repair or suppress the summary instead of letting `no_problems` policy hide actionable prose without locations. Do the same when skip/summary prose asks a human to provide diff/source context or attribution context; agents must request concrete files via `aicr.fetch_more_context` or verified line attribution via `aicr.try_blame`.
- Built-in IM summaries must include the event username when present, rendering `@username (Display Name)` when both normalized username and display name are available. Platform-native mention tags (`<at>`, `<@user>`, etc.) are handled by the author-resolution layer via `MentionChannelKind`; templates render only the human-readable form.
- `vcs.workspace` is submitter metadata captured from the event payload; do not substitute analysis/client workspaces from adapter configuration into user-visible IM output.
- P4 directory attribution checks submitter workspace segments before account email/username after explicit mappings and blacklist checks. Shared accounts such as `admin` can match another member's email local part; that match must not override a unique workspace owner. A tied workspace tier blocks weaker account/model fallback. Preserve non-P4 precedence and `guess_author: false`; assert the native mention in `channel-identity.test.ts` and `feishu-app-publishing.test.ts`, while retaining the original account in the displayed author.
- `feishu_app` shares the webhook card builder and template assets. Resolve directory-based mentions before rendering custom `atMentions`; card mentions use `<at id="ou_..."></at>`. Never convert raw VCS logins into Feishu IDs. Match only available group/profile fields with an unambiguous highest-priority result; a tied tier blocks weaker guesses and `all` fallback. Only transient transport/HTTP 429/5xx failures may reuse an expired snapshot with a warning; every later call retries. Permission rejections and incomplete membership invalidate it. Without a usable snapshot the report sends without mentions; profile permissions may limit enrichment. Directory TTL resolves channel `member_directory.cache_ttl_seconds` → global `outputs.author_resolution.directory_cache_ttl_seconds` → 12h default (0 disables reuse and retention, max 7d). Keep the host-side `ChannelUserDirectory` boundary and generation-scoped caches; review MCP tools must not receive full directories. Verify static and database TTLs through actual old/new publication in `runtime-generation.test.ts`, plus `feishu-app.ts`, `feishu-members.ts`, and `feishu-app-publishing.test.ts`.
- Classify identity capability before association: Git channels preserve native resolution; webhook bots cannot list users. Only directory channels can invoke a dedicated identity model after exact matches and workspace rules fail. `guess_author` defaults to true for Feishu applications; `mention_author` still gates directory access and notifications. Do not inject directory data into main review prompts, logs or report state. Only the dedicated `author-identity.ts` prompt may receive names, aliases, emails and submitter hints, with opaque candidate keys; the host validates returned membership and renders @. Uncertain/invalid output and timeouts cannot escalate to `all`. Keep all three `author_resolution_model_chain` references database-manageable and generation-pinned; fallback is the global `default_model_chain`, independent of workspace review/triage groups. Test actual old/new publication and budget gates in `runtime-generation.test.ts`, plus channel skips and cancellation during gateway retries.
- VCS usernames and delivery actors are not IM user IDs. Without a directory, webhook bots require explicit email mappings; social IM uses its channel-local typed mappings below. A file directory replaces that fallback, including custom `atMentions` before rendering; disabled, unavailable or ambiguous directory matching must not emit raw-login or `all` mentions. Cover P4 workspace owners and disabled mobile reminders in `member-directory-publishing.test.ts`.
- Social IM uses channel-local `author_mappings`: native user IDs without a directory, snapshot user IDs for API sources, local member keys for files. Directories/mappings enable reminders unless `mention_author: false`; `guess_author` defaults false. Reuse the blacklist and ambiguity rules. Slack/Discord API snapshots are bounded and complete; Telegram uses mappings/files. Never pass native controls through general report text: append the resolved mention after escaping, reserve its size, use Discord's exact users allowlist and Telegram UTF-16 text-link entities. Keep directory reads outside callbacks and authorization. Test raw payloads in `social-im-author-mentions.test.ts` and cache/pagination/format boundaries in `social-im-mentions.test.ts`.
- Measure the final UTF-8 content/request: WeCom webhook Markdown 4096 bytes, Feishu webhook request 20 KiB, Feishu application card request 30 KiB including the serialized card, recipient and recovery UUID. Only excess reports receive a truncation notice; preserve native mentions, detail links and action buttons. WeCom application reports retain their 2048-byte splitting and receipts. Test Chinese, emoji, JSON escaping and exact boundaries in `im-report-limits.test.ts`; do not add webhook parts without updating publication recovery's one-message rule.
- Each IM platform uses a dedicated transformer in the modules above (Feishu JSON 2.0 preserves headings/tables/code in `card.body.elements`; WeCom uses its supported Markdown subset). When adding a new IM channel, implement a matching transformer before wiring the dispatcher.
